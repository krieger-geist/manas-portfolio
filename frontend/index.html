The idea I follow

Evidence over assumptions. Something is "fixed" when a check confirms it.

A lot of time in an outage goes into guessing. I try to build systems that measure first, change as little as possible, and check the result before calling it done.

What that looks like in RELAY AEGIS (example run from my demo):

relay-aegis · incident log
$ chaos stop-db --healing on
✗ health check failed: postgres: connection refused
✗ health check failed (2/2) → incident opened
→ evidence: container exited, dependency down
→ diagnosis: database stopped · confidence high
→ policy: RESTART_DEPENDENCY allowed · attempt 1/3
✓ action executed
✓ verified: 3/3 health checks passing
● resolved · no human action
01

Measure before you fix

Health checks, logs and metrics come first. A diagnosis needs evidence, not a hunch.

02

Make failure boring

Design for things breaking: timeouts, retries, safe automatic recovery and clear runbooks.

03

Small, reviewed, verified changes

Test each change on its own, get it reviewed, and call it done when the checks pass.

04

Leave it simpler than I found it

Clean APIs, written docs and a handover your team can follow.
